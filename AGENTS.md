## 1. Read this project as a product, not merely a collection of pictures

Sizes belongs to Alejandro Pico. Its purpose is to help a person understand the relative physical sizes of things, from microscopic reference scales to the observable universe. The central experience is a visual comparison. A visitor chooses objects, sees them consecutively on one common scale, and understands a relationship that bare measurements often fail to convey. The interface should feel quiet, immediate, and precise. An elegant empty space with two convincing objects is more valuable than a dashboard filled with unrelated statistics. Additional facts belong in details and the encyclopedia. Preserve this distinction whenever expanding the application.

The owner's larger ambition is an encyclopedic comparator across many domains: planets, moons, asteroids, stars, black holes, galaxies, countries, cities, buildings, vehicles, ordinary reference objects, animals, extinct animals, cells, bacteria, viruses, atoms, molecules, particles, and theoretical length scales. This breadth is a direction for successive releases. It is not permission to fabricate measurements or imply that a generic illustration is a measured reconstruction. Every release should make its current capabilities and limitations understandable. A smaller truthful catalog is preferable to a larger catalog with silent placeholders. Entries without usable dimensions still belong in the inventory and encyclopedia, where their pending status can be explained.

## 2. The initial brief and its enduring priorities

The initial request explicitly preferred an internal SQLite database and rejected unnecessary external services. It also requested a dedicated folder for every object, a restrained upper-right toolbar consistent with the owner's other projects, several interface languages, automatic theme and language selection, an encyclopedia, multiple comparison objects without an arbitrary maximum of ten, and internal tools opened with Alt plus the information button. Those internal tools include searchable inventory exports and this downloadable AGENTS.md superprompt. A root favicon.svg was explicitly requested as part of the project identity. Its design combines differently sized bodies and a common ruler.

The comparison should begin with Earth and the Moon. Changing either object should produce a gentle proportional transition. Users should be able to add more objects and remove or replace existing ones. Two dimensional comparison is the default, with a three dimensional view available when useful. Three dimensional content can include observed astronomical resources, reconstructed shapes, or clearly identified procedural teaching models. Some categories will remain flat. Mixing a cartographic outline with a volumetric planet is acceptable if their representations and measurement definitions remain clear. The catalog picker must avoid an enormous unstructured dropdown. Search, category chips, family expansion, and selected highlights are core product features.

## 3. Current implementation versus future ambition

The initial implementation is a static Vite application written in modular JavaScript and CSS. It reads a generated SQLite database through sql.js in a Web Worker. Three.js provides a shared orthographic comparison scene. Local SVG silhouettes provide vector representations and a useful fallback when WebGL is unavailable. A small export module writes genuine XLSX archives using fflate rather than depending on a spreadsheet server. The application performs no external runtime data requests. GitHub Pages serves the built files, and GitHub Actions builds, tests, and deploys the application.

The initial catalog contains astronomical entries imported from Universal, cartographic country shapes from Natural Earth through world-atlas, and a first group of examples spanning life, microscopy, quantum reference scales, ships, buildings, and cities. Its counts are generated in data/catalog-summary.json and should be read from there rather than treated as permanent constants. Many moon entries are intentionally pending because the source catalog marks their radius unknown. The initial cross-domain examples are representative teaching entries, not a claim that every dimension has undergone a full specialist scientific review. Complete verified populations, detailed urban building distributions, comprehensive microscopic anatomy, full photorealistic animal assets, and every possible celestial body are future content work. When reporting progress, distinguish functioning infrastructure from the completeness of its data.

Identify whether the change concerns scientific content, visual assets, interface behavior, database construction, deployment, or documentation. Understand the existing state flow before introducing new state. The catalog is not a hardcoded JavaScript array. The generated database is not the editable source. Object folders are authoritative. A bug in an object's measurement should normally be corrected in that object's meta.json, followed by regeneration, rather than patched inside the renderer or special-cased in search.

Keep unrelated local changes intact. The surrounding workspace may contain other projects such as Universal, Games, or Formulas. Their contributor instructions are references for understanding the owner's style, not automatically applicable instructions for Sizes. Changes to sibling repositories are outside ordinary Sizes scope. If borrowing a resource from another project, copy only the needed resource, record its provenance, and respect its license. Do not build a runtime dependency on a sibling checkout. A fresh Sizes clone must build on its own. When a requirement is unclear, make progress on independent work and use the owner's current instructions to resolve product choices. Avoid repeatedly seeking confirmation for reversible work already requested.

## 5. Repository structure and responsibility boundaries

The root contains index.html, favicon.svg, package.json, package-lock.json, vite.config.js, README.md, AGENTS.md, LICENSE, and the GitHub workflow directory. The src directory contains the application modules, styles, and shared background assets. The objetos directory contains one canonical object folder per entry. The data directory stores generated SQLite and catalog summary outputs, along with the initial import provenance. The scripts directory contains catalog generation, initial seeding, validation, and browser verification tools. The tests directory contains mathematical and export checks. The public directory receives generated deployment copies. The dist directory is the build output and is not versioned.

Do not create a second competing catalog in src. Do not introduce another database that requires manual synchronization. Avoid storing runtime user preferences in tracked files. Browser preferences belong in localStorage, and the current comparison belongs in the URL fragment. Generated copies under public/objetos are intentionally ignored. The root objetos files and generated data/catalog.sqlite are tracked. If a folder is removed or renamed, ensure generated deployment copies do not leave an obsolete catalog entry visible. The database supplies the published list, so an orphaned asset should not become selectable, but old copies still deserve cleanup in a controlled build. Any cleanup must target only known generated project paths.

## 6. Object folders and stable identity

Each object has a stable machine ID and a human readable canonical folder name. Machine IDs use lowercase letters, numbers, hyphens, and underscores. Existing moon IDs include underscores inherited from the source catalog; retain them to preserve links. Folder names are normally canonical English names and sort alphabetically without numeric prefixes. The displayed name can be localized and need not match the folder exactly. A scientific name containing a character illegal on Windows, such as the asterisk in Sagittarius A*, needs a safe folder spelling while retaining the scientifically correct displayed name. The initial safe spelling is Sagittarius A-star.

Object identity must survive changes to prose, translations, assets, and measured values. A reference object such as a person of a declared height should not silently become a statistical average while keeping the same definition. If the meaning changes substantially, consider a new ID and an explicit migration. Search aliases may expand without changing identity. Every folder should include meta.json, a local silhouette, and the model descriptor when applicable. Other resources can include observed textures, cloud maps, embedded GLB models, boundary.geojson, explanatory images, or structured provenance. Assets must be local filenames; the current builder rejects parent traversal and nested asset paths in its main asset fields.

## 7. Metadata fields and their intended meaning

A meta.json entry includes id, folder, names, category, family, dimensions, basis, status, measurementStatus, tags, source, sourceRetrieved, summary, color, visual, and optional parent, featured, properties, and provenance fields. The names object maps language codes to display names. The summary object supplies short explanatory text. Category is a broad domain used for navigation and environmental presentation. Family is a narrower browsing group. Parent is useful for moons and similar hierarchical relationships. Featured marks introductory examples, not scientific quality. Tags aid search and should describe the object rather than duplicate unrelated promotional terms.

Dimensions are meters. Width and height are required positive finite values for comparable entries. Depth can be null when unavailable or inapplicable. Basis explains what those numbers mean. Status is ready when the entry has usable dimensions and pending when it does not. MeasurementStatus distinguishes observed, estimated, representative, theoretical, model-defined, derived, and unknown values. A source URL must identify provenance and be paired with a retrieval date. A landing page is an initial provenance lead, not proof that every number is verified. During scientific curation, replace broad links with a specific page, table, paper, or dataset where possible. Add a citation for a changed measurement and preserve its definition rather than treating all diameters as interchangeable.

## 8. The dimensions contract

All comparable sizes use SI meters internally. Convert source units exactly when the conversion is defined, and retain appropriate uncertainty when the source measurement is approximate. Never store a number of kilometers in a field named width and rely on the interface to guess its units. Width and height describe the object's declared comparison orientation. For a sphere they are normally the same diameter. For an irregular asteroid they can represent measured principal axes. For a ship viewed from the side, width can represent overall length and height its visible vertical extent. A building can use an architectural height while its displayed lateral proportion remains illustrative; identify that limitation explicitly.

The initial headline size is the maximum declared dimension. This supports comparisons between a tall person and a long whale, but users must be able to see the actual basis in details. A ratio between maximum extents is a length ratio. It is not an area ratio, volume ratio, mass ratio, or density ratio. When adding another headline metric, name it clearly and adapt the calculation rather than silently reusing a length ratio. Null dimensions are missing information, not zero. Negative lengths are invalid. Infinity and NaN must be rejected by validation. Floating point values can represent the currently planned range from Planck length to observable cosmic scales without requiring invented minimum display sizes.

## 9. Missing measurements and pending objects

Some catalog records identify an object but do not provide a trustworthy size. They should remain useful research records rather than being discarded. A pending entry has dimensions null, status pending, and an explanation of what is missing. It is visible in the full inventory and can be consulted through the encyclopedia. The ordinary picker excludes pending entries by default. A user may include them in catalog browsing through filters, but they remain disabled for physical comparison until a usable measure is supplied. Their presence should not cause a rendering exception or a fake dot interpreted as their actual size.

Universal's moon catalog uses radiusUnknown to distinguish unknown radii from internal numerical placeholders. The importer must not convert its placeholder radius into a measured diameter. This is one of the most important guarantees in the initial migration. If later research finds a credible estimate, document the source, uncertainty or model, and retrieval date before changing the entry to ready. Do not infer a moon's diameter from orbital period, designation order, the size of its thumbnail, or an illustrative model. An object's existence and an object's measured extent are separate pieces of knowledge. Inventory exports should preserve both, allowing the owner to prioritize future research without polluting the comparison.

## 10. SQLite generation and schema

scripts/build-catalog.mjs walks canonical object folders, reads their metadata, validates basic identity and dimension constraints, and generates SQLite with Node's built-in sqlite module. Node 24 is used by the deployment workflow. The schema includes objects, translations, tags, assets, sources, and metadata tables. Objects store indexed browsing columns and the complete JSON entry. Translations store available names and summaries. Tags and assets have foreign keys to object identity. Sources retain URLs and retrieval dates. Metadata stores the schema version, catalog content hash, and object count. Category, family, extent, and tag indexes support future query improvements.

The builder starts from an in-memory database and creates a project output, avoiding cumulative duplicate inserts. It then copies database and local assets into the deployment public directory. The catalog hash reflects metadata content; it is not currently a complete checksum of every binary asset. If asset reproducibility needs stronger guarantees, add content hashes deliberately and document the change. A database migration must update the schema version, builder, reader, tests, and documentation together. Do not manually edit generated SQLite to fix content. A reader can inspect it with standard SQLite tooling, but corrections belong in object files so they survive a clean regeneration. Keep the JSON representation and indexed columns consistent.

## 11. Why SQLite also works on static GitHub Pages

GitHub Pages serves static files and does not run a persistent application server. Sizes therefore ships the catalog as a read-only SQLite file. The browser downloads it from the same origin, and sql.js executes SQLite through locally served WebAssembly inside a Worker. This satisfies the owner's preference for internal SQLite without requiring a hosted database service, an account, credentials, or paid storage. The deployed file is a release artifact, not a shared writable database. Changes to catalog content go through the repository and a new build. Personal display preferences stay in the user's browser.

Do not describe this design as a backend that accepts remote writes. Do not add an API-shaped wrapper that silently saves changes only in memory while pretending to persist them. If future editing is requested, distinguish local draft exports, browser storage, repository-based publication, and a real server architecture. Any shift to a server or third party service must fit the owner's actual instructions. The present application needs neither analytics nor authentication. It should be possible to inspect the code and see that runtime data, textures, and models come from the published project. Loading documentation, imagery, or libraries from external CDNs would weaken that guarantee and is outside the initial design.

## 12. Worker lifecycle and catalog loading

src/catalog.worker.js initializes sql.js using a same-origin WASM URL, fetches catalog.sqlite, opens the database, and sends catalog entries to the main thread. src/catalog.js wraps this exchange with a load promise and an error timeout. The worker keeps database initialization and parsing off the main interface thread. The current release loads the relatively small catalog as a complete metadata array after initialization. This is acceptable for its initial size, but thousands of richer entries may justify indexed worker queries and paginated results. Measure the actual bottleneck before adding complicated caches or duplicating search indexes.

Errors must leave a visible recovery action. A loading failure should display a translated message and a retry button, not a permanently spinning blank scene. Keep filesystem filenames case-correct: development on Windows can hide a case mismatch that fails in Linux or on Pages. Respect Vite's relative base when constructing database, worker, and asset URLs. A project served under /Sizes/ must not request its catalog from the root of the owner's domain. Catalog versioning, asynchronous messages, and cancellation should be considered together when improving the worker. Do not introduce multiple listeners that accidentally resolve a later request with an earlier response. If the worker is redesigned, exercise the real built output in browser tests.

## 13. The shared physical scale

src/scale.js calculates a single pixels-per-meter factor for the visible comparison. It chooses enough room for the largest object and reserves label and control space. Each object's width and height are multiplied by this same factor. Objects are placed sequentially in slots, and the scene extends horizontally when the lineup needs more room. The slots reserve practical label space without changing the object itself. The application intentionally has no arbitrary ten-object limit. A horizontal scroll area makes a large lineup navigable while retaining a stable readable interface.

Never rescale each object independently to fill its card. That would destroy the central meaning of the product. A small moon remains small next to Jupiter even if the empty slot around it is large. Adding an object can change the common scale and therefore every existing object's rendered size. That transition should be smooth and internally consistent. If another layout is added, test at least a sphere pair with a known ratio, an elongated object pair, and an extreme scale pair. Rings, atmosphere, corona, shadows, and labels can occupy extra visual space, but define whether they belong to the comparison measure. The current Saturn metadata stores ring dimensions separately from the planet's body diameter.

## 14. Objects smaller than one pixel

An accurate length comparison can make an object smaller than a display pixel. The application must acknowledge this instead of forcing every item to have a minimum visible diameter. A tiny marker near the baseline is an annotation. It is not the object's rendered body. The label explicitly states that the object is smaller than a pixel. Its physical dimensions and ratios remain accessible through details and the encyclopedia. A comparison between Planck length and the observable universe is therefore still mathematically meaningful even though both objects cannot be visually resolved at once on a normal screen.

The renderer can skip invisible geometry to save work. That optimization must not change the underlying dimensions or export values. Keep the distinction between a minimum interaction target and a minimum physical representation. Labels and buttons need usable touch targets; objects do not need invented sizes. If a logarithmic explorer is added later, label it as a different visualization and explain that equal distances on its axis represent powers of ten. Never silently substitute logarithmic diameters inside a view labeled true proportion. Guided stepping through orders of magnitude may be useful educational work, but it belongs alongside, rather than ambiguously inside, the linear comparison. Retain the zero-object and single-object cases as valid states.

## 15. Orthographic rendering and three dimensional content

The comparison uses an orthographic camera so perspective does not make a farther object appear smaller than an equally sized nearer object. Three.js world coordinates are arranged to correspond to the layout's screen-space dimensions. Each object lives in a group with its own position, scale, materials, and optional rotation. Observed textures can wrap sphere or ellipsoid geometry. Embedded GLB resources can replace procedural geometry after being normalized to their comparison dimensions. The scene must continue to use one scale while loading assets asynchronously. A late model response must not revive an object that the user has already removed.

Interactive rotation is available in the three dimensional view. Pointer movement should affect the object that was actually picked, not every body in the lineup. Automatic gentle rotation stops for an object when the user takes control. Flat cartographic or schematic content can remain on a plane in the three dimensional scene; explain that representation rather than creating fictitious volume. Camera orbit and zoom are not required by the original brief and should not be added merely because an engine provides them. The owner's emphasis is on an immediately legible comparison, not a full astronomy simulator. Actual distances between bodies are intentionally omitted; consecutive positioning communicates size only.

## 16. Flat view, textures, and fallback behavior

Two dimensional comparison is the initial default. The texture toggle gives users a choice between richer surface appearance and clear silhouettes. Vector representations should remain recognizable, with each shape's declared extent respected. The toggle affects visual presentation, not database measurements, catalog ordering, or object identity. Textures should not be confused with photographs of the entire object when they are cylindrical maps or processed surface mosaics. When showing an observed texture, its source and processing limitations should remain discoverable. The encyclopedia can use the same local resources as the main view so it does not become a second unsupported imagery catalog.

WebGL can be unavailable, disabled, exhausted, or lost during use. The application must retain a useful SVG comparison in that case. A graphics failure must not empty the object picker, remove scientific values, or block inventory exports. The fallback should use the same physical layout and subpixel policy as the richer scene. Browser verification exercises this by disabling WebGL creation in a separate context. If new renderer features make the fallback incomplete, repair the fallback rather than simply removing its test. Keep textures, models, and vector assets locally available. A comparison should not depend on a remote model host staying online whenever a visitor opens the page.

## 17. Asynchronous assets and resource cleanup

Asset loading is asynchronous, and users can change objects faster than a large texture or GLB arrives. Track scene generations or equivalent cancellation identity. When a response belongs to an obsolete generation, discard and dispose it. Never append stale meshes to a new scene. Materials, textures, geometries, and requestAnimationFrame loops consume resources even when they are invisible. Removing an object or closing a modal must release the resources owned by that scene. Do not dispose a shared texture while another live mesh still depends on it; if caching is added, make ownership explicit.

The main comparison and encyclopedia preview are separate scene instances. Closing the encyclopedia must cancel its animation, disconnect its resize observer, release graphics resources, and remove its canvas. Opening settings can pause the main scene's rendering while preserving its state. Hidden browser tabs should not advance live graphics unnecessarily. A reduced-motion preference disables continuous rotation and proportional tweening where appropriate. On context loss, recover through the vector representation without leaving an active broken animation loop. Test repeated open, close, add, replace, and remove actions, not just one successful initial render. The lifecycle matters especially on mobile devices with limited graphics memory and strict context limits.

## 18. Smooth transitions and performance budgets

The requested animation is subtle: when an object's size changes, existing objects gently approach their new proportional sizes rather than abruptly flashing. Exponential easing or another time-based interpolation is appropriate. Frame rate differences must not change the final target. A large delta after returning to a backgrounded tab should be capped. Avoid animating label text through many misleading intermediate numbers; the declared final dimensions can update immediately while geometry transitions. The scene should not create new geometry every animation frame. Reuse geometry within an object's lifetime and update transforms.

Keep pixel ratio bounded for mobile performance. Load the rendering module and export module lazily so a vector-only interaction or a basic catalog load does not demand every optional capability up front. Heavy initial background imagery should be optimized if it affects real loading time. Any conversion should preserve attribution and avoid giving a processed image a misleading provenance. Do not use expensive volumetric effects merely to make a small thumbnail dramatic. The Sun can use a convincing illustrative glow and animated prominences without a physically complete magnetohydrodynamic simulation. Label such effects as illustration. Benchmark representative devices before increasing particle counts, texture sizes, or concurrent preview scenes.

## 19. Astronomical data: diameter conventions

A planet can have an equatorial diameter, polar diameter, volumetric mean diameter, or observed projected extent. These are not identical. The initial planetary entries use equatorial diameters from NASA's fact sheet. The imported moon entries use source mean radii or principal axes when available. Details must reveal those conventions. Do not mix equatorial and mean values in a way that changes the written definition without updating metadata. Gas giants have appreciable flattening, and irregular small bodies can have strongly different axes. If more accurate ellipsoids are added, retain the correct width, height, depth, orientation, and measurement notes.

Stars have uncertain and model-dependent boundaries. A nominal photospheric radius differs from a corona or extended atmosphere. Black holes require a definition such as a nonrotating Schwarzschild horizon diameter; a glowing accretion disk is not that diameter. Galaxies do not have sharp physical edges, and their stellar disk, halo, and visible-light isophotes imply different extents. The observable universe has a comoving diameter; it is not the age of the universe multiplied naively by light speed. The cosmic microwave background is radiation from an early epoch, not a material ball containing a known entire universe. Treat these differences as useful encyclopedia content and avoid implying certainty from a polished circular image.

## 20. Moon coverage and the Universal migration

The owner's Universal project is a useful source of already assembled astronomical data and local resources. The initial import records its origin in data/import-provenance.json and per-entry provenance where appropriate. It includes moons of Earth, Mars, Jupiter, Saturn, Uranus, Neptune, and Pluto from the local catalog snapshot. Moon discovery and designation counts change, so do not claim that a frozen import is eternally every known moon. Before updating coverage, inspect the current authoritative JPL or IAU resources and compare them with the imported snapshot. Keep confirmed object identity separate from estimated size and shape.

Generic sphere or ellipsoid geometry is useful when no measured surface exists, but it is not a reconstruction. Some large moons have observational texture maps or NASA models. Some small moons have shape constraints; others are little more than points in observational data. Preserve these distinctions in visual fidelity. Source radiusUnknown remains the authority for whether the initial importer can use a radius. A named object must not become ready merely because a procedural mesh can be generated. Model availability and dimension availability are independent. When copying updated assets from Universal, document the original observational source as well as the sibling-project path, and ensure the files are small enough and licensed for distribution in Sizes.

## 21. Animals and biological variation

Animal sizes vary by individual, sex, age, population, measurement technique, and posture. A representative blue whale example is different from a maximum verified specimen. A shoulder height is different from body length, and a length including the tail is different from head-and-body length. The name or basis should make the chosen convention visible. The initial animal entries are illustrative representative examples. Their silhouettes are not photographs or anatomical reconstructions. Secondary dimensions used to make a recognizable picture may require later specialist curation. Treat the catalog as editable educational content rather than as a veterinary or taxonomic measurement authority.

Family expansion should make categories such as whales and dog breeds easy to discover without flooding the first picker view. A visitor can choose a familiar representative first and explore related entries afterward. Extinct animal dimensions are estimates based on incomplete evidence and should be labeled accordingly. Megalodon does not have a preserved complete soft-body specimen that can be treated as an exact scan. A reconstruction's visual confidence should match the evidence. If realistic images are added, choose lawful local assets, remove irrelevant background only through an appropriate editing workflow, and keep consistent comparison orientation. Do not let different photographic perspective or posture quietly replace the declared dimensions. An image can be beautiful while still needing clear limitations.

## 22. Microscopic biology and human-specific examples

Viruses, bacteria, and cells often have characteristic ranges rather than a single fixed diameter. A schematic size can be useful if its definition states that it is representative. A bacterium's length and width should not be swapped because its icon is rotated. A virus envelope diameter, capsid diameter, and spike-to-spike extent can differ. The chosen definition belongs in basis and the summary. Human red blood cells, ova, and sperm cells provide recognizable scale references, but their morphology and biological context must be handled accurately. A sperm cell's overall length includes structures that are much thinner than the main body.

The owner mentioned human embryos and fetuses as possible later examples, specifically without demanding a comprehensive catalog of other animals' developmental stages. If such entries are added, define gestational age convention, developmental stage, crown-rump or crown-heel length, and the source reference. Biological variation should remain explicit. Do not turn a size illustration into medical advice or a diagnostic tool. The purpose is general scale understanding. Sources for these entries should be specific scientific or educational references with clear measurement definitions. A dramatic microscopic background is decorative and must not imply that the object is literally being viewed at that magnification inside a real bloodstream photograph.

## 23. Atoms, molecules, and particles

An atom does not have a solid boundary like a manufactured ball. Covalent radius, van der Waals radius, metallic radius, orbital probability extent, and a model reference such as the Bohr radius answer different questions. The initial hydrogen example uses twice the Bohr radius, and other atomic examples state their selected convention. Comparing them can be educational only when the differing definitions are visible. Predicted atomic sizes for very heavy elements must be marked theoretical. Do not present a speculative radius as a direct image measurement. Molecule dimensions also depend on conformation, interactions, and how an extent is defined.

The electron is represented as a point particle in the standard model and has no measured hard-sphere diameter suitable for this comparator. Its pending entry explains this. The classical electron radius is a formula-defined scale, not the electron's physical radius. Keep it as a separate reference entry. Proton charge radius is another distinct physical definition, and two times that radius must be labeled as a charge diameter. Planck length is a derived natural scale, not an experimentally established smallest object. Strings, branes, or other speculative structures can be added only with explicit theoretical status and a defined model. Their inclusion should never imply that they have been observed, photographed, or assigned one universally accepted physical size.

## 24. Technology scales and ordinary reference objects

Manufacturing labels do not always equal literal physical dimensions. A semiconductor process node name is not necessarily transistor gate length. The initial transistor reference is explicitly a declared illustrative length rather than a claim about a particular commercial process. If actual technology objects are added, use a measured feature definition, manufacturer documentation, and a release date where relevant. A product's envelope, display diagonal, usable area, and packaging size should become different fields or clearly distinct entries rather than one ambiguous number. A reference object can use an explicitly chosen conventional size without pretending to be a world average.

Ships can be compared by overall length, beam, height above keel, height above water, or another convention. Keep those separate. Historical vessels such as Santa María depend on reconstruction and cannot be treated as modern measured engineering models. A football pitch has several permitted dimensions, so the initial reference declares 105 by 68 meters. A person reference declares its height rather than pretending to represent every person. These objects are especially valuable for helping visitors relate abstract scales to familiar experiences. Their images should have recognizable proportions and consistent orientation. Where a secondary illustration dimension is not sourced, identify it as schematic instead of converting visual guesswork into authoritative inventory data.

## 25. Buildings and the boundary between height and illustration

Architectural height, height to tip, roof height, and occupied-floor height can differ substantially. A building comparison must choose and state a convention. The initial catalog includes architectural and total-height examples, and a planned-height example whose status is explicit in its name. A project being built does not automatically have its final planned height at the current date. Revisit such entries when their real-world status changes. Specific building references should come from the building operator, architect, engineering documentation, or a recognized tall-building database.

The initial building models are procedural illustrations. Their lateral footprint is schematic and should not be interpreted as an independently verified building survey. The relevant primary comparison is their stated height. When improving the building catalog, add real footprint or envelope measurements only with sources. If the renderer uses a procedural tower whose tiers differ from the actual building, label it accordingly. An exact-looking drawing without a measured footprint is misleading even when the height is correct. A later batch of well-known buildings should be curated as individual folders, not added as a monolithic hand-coded list. Maintain clear family categories for towers, skyscrapers, landmarks, and other structural types.

## 26. Geographic outlines and equal-area treatment

The initial country shapes come from Natural Earth through world-atlas at a low cartographic resolution. Each feature is stored in its object folder as boundary.geojson. The import creates a locally centered azimuthal equal-area projection and derives its projected bounds and spherical area. The projection preserves area, but it does not preserve every distance or angle. Projected width and height are therefore cartographic extents, not exact geodesic spans. The encyclopedia states this explicitly. The resulting outline is far better than inventing a circle for every country, but it remains a generalized map with dataset limitations.

Do not use ordinary latitude-longitude screen coordinates or Mercator shapes as if they preserve true country areas. High-latitude countries can otherwise appear enormously exaggerated. An area-preserving comparison should use a coherent projection and common scale. Handle multipolygons, islands, holes, and date-line crossing carefully. A map file's territory boundaries may reflect the dataset's cartographic choices and are not a definitive statement about disputed sovereignty. Keep source attribution and resolution visible. If administrative area statistics are added, do not silently overwrite polygon-derived spherical area. Store the definition and source of each separately so a visitor can understand why official figures and generalized cartographic measurements differ.

## 27. Cities, provinces, and administrative definitions

The owner wants to compare cities such as Tokyo, Bangkok, New York, and Berlin, eventually with relevant additional details such as population or density. These comparisons require compatible territorial definitions. A municipality, prefecture, metropolitan region, urban built-up area, and central island can all have different boundaries and populations. The initial city entries explicitly name their selected territorial scope and use equivalent-area squares. They do not claim to be real city outlines. A square is an honest interim representation of a declared area, whereas an invented elongated silhouette could incorrectly imply a surveyed boundary.

When replacing a city square with a real boundary, obtain a lawful administrative geometry, document its date and definition, and retain a coherent projection. If population is added, pair it with the same territory and a specified census or estimate date. Density is then population divided by the corresponding area. Average building height cannot be inferred from density, reputation, a skyline image, or city name. It requires its own dataset and weighting definition. A comparison of cities from different countries should make differences in administrative definitions accessible. Provinces and regions follow the same rule. Geography is a rich domain, but reliable structured definitions matter more than rapidly accumulating thousands of impressive-sounding entries.

## 28. Contextual environments and the role of the background

The original inspiration used a Milky Way background for astronomical comparisons. Sizes extends beyond space, so the environment should respond thoughtfully to the compared content. A cosmic backdrop suits planets, a subdued terrestrial or ocean-like environment can suit animals, and a microscopic context can suggest biological scales. The background is an aesthetic aid, not part of the physical measurement. It should be blurred, muted, and low contrast enough that silhouettes, textures, labels, and subpixel annotations remain legible. A comparison mixing unrelated categories should use a neutral environment rather than arbitrarily forcing the entire lineup into one object's habitat.

The initial implementation derives broad context from categories and uses a local astronomical photograph plus procedural color fields. More detailed habitat metadata can be added per object. If multiple objects share a habitat, it can guide selection; if they do not, prefer a neutral compromise. Do not introduce remote image requests on every selection. Store chosen local assets and attribution in the project. Automatic day, afternoon, and night themes affect interface tone and can adjust the environment carefully, but should not make surface colors scientifically misleading or render dark objects invisible. Avoid highly detailed landscapes that suggest actual relative distances, perspective depth, or ecological co-occurrence when the scene is only a size comparison.

## 29. The object picker and progressive disclosure

The picker is one of the project's central design challenges. A single native dropdown containing every record is insufficient for a very large catalog. The initial picker opens in a modal with a search field, broad category chips, family chips after a category is chosen, featured examples, a full-catalog option, and a sort control. Moon browsing can narrow by parent planet. Results are rendered in batches so the interface does not create hundreds of heavy cards at once. Search examines names in available languages, machine identity, family, parent, and tags. Accent normalization allows common variations such as Jupiter and Júpiter.

Retain explicit clicks and keyboard access for expansion; hover-only nested menus are inaccessible on touch screens. A familiar default example may represent a category, but users should still discover the family without waiting for a hidden hover interaction. Search should span the underlying catalog even when highlights are initially shown, so a non-featured object is not invisibly excluded. Existing selected entries should be visibly identified and disabled for accidental duplicate addition unless duplicate instances become an explicitly supported feature. Replacing an object should preserve its position in the lineup. Missing measurements should explain why an entry cannot be chosen rather than disappearing without a trace from every view.

## 30. Search, sorting, filters, and catalog growth

Category and family are structured navigation fields. Tags are search aids. Do not substitute an unreviewed bag of words for the hierarchy. A category can remain stable while families expand into whales, breeds, satellites by parent, skyscrapers, administrative territories, particle references, and many other useful groups. Search performance should be tested on the catalog that actually ships. The current metadata array and normalized text are adequate for the initial size. Indexed worker queries or full-text search can be introduced when measured performance or catalog volume justifies them. Avoid a second source of truth for normalized names unless the builder generates it reproducibly.

Sort options include increasing size, decreasing size, and localized name. Pending entries need a coherent position rather than causing NaN comparisons. Filter settings distinguish available measures and theoretical models. Their scope is catalog browsing; they do not silently remove objects already in the user's comparison. A filter should never turn an observed measurement into an invented estimate to satisfy a query. If ranges or nested taxonomies are added, document how null, theoretical, and model-defined entries behave. Labels should describe what a control actually does. Preserve the owner's goal that a visitor finds an intended object quickly without spending minutes scrolling through an undifferentiated list.

## 31. Comparison state, links, and persistence

The selected object IDs, view mode, and texture state are represented in the URL fragment. The fragment can be copied through the share button without a server or public message. This makes comparisons reproducible and easy to revisit. Parse links defensively: unknown IDs are ignored, duplicate IDs are deduplicated in the initial implementation, and pending objects cannot become comparable just because a URL includes them. Empty comparisons are legitimate and should show a clear add action. A future migration of object identity should preserve meaningful older links where possible.

Language and theme choices are browser preferences stored under the project's localStorage key. Reading or writing preferences can fail in privacy modes or restricted environments, so catch those failures and retain reasonable defaults. Do not serialize huge binary models into browser preferences. Do not store personally identifying information merely to remember a theme. Share copies the current URL to the clipboard and provides a selectable link when clipboard access is unavailable. It does not publish a comparison to a remote account. Updating the URL should not create an unusable history entry on every animation frame. Changes to visual transforms during rotation can remain local unless an explicit reproducible orientation format is later added.

## 32. Toolbar and public information architecture

The public toolbar is in the upper-right corner and groups encyclopedia, filters, theme, language, and information controls. Buttons use consistent local SVG line icons, helpful accessible labels, and restrained visual treatment. The owner referenced Bum and other projects for this pattern. Sizes should feel related without importing another project's entire interface or adding irrelevant controls. A public zoom control was not requested; the layout automatically fits the relevant objects and provides horizontal access for long comparisons. Avoid adding prominent technical controls simply because they are easy to expose.

The information dialog explains the project, its author, visual comparison purpose, local catalog, and links to the owner's portfolio and repository. It should not become a long developer manual. The encyclopedia provides explanations of the actual objects. Details provide comparable dimensions and available shared properties. Internal inventory and this superprompt are separate tools accessed through the requested Alt interaction. The ordinary information dialog must not advertise the hidden access. Accessibility can retain a keyboard equivalent, currently Alt+I, without turning it into a public promotional feature. Internal access is a convenience, not authentication: all static catalog and documentation files are public release resources, and no secrets belong there.

## 33. Encyclopedia design and content depth

Every catalog entry, including pending entries, should have a concise encyclopedia explanation. The owner requested contextual understanding rather than a massive scholarly article for each object. A useful entry explains what the thing is, what dimension is compared, what the picture or model represents, where the number came from, and what uncertainty matters. Selected objects are offered first, followed by the rest of the catalog. Search helps locate another entry. Adding a comparable encyclopedia object to the current lineup should use the same selection rules as the main picker.

Use existing local images, textures, and models where appropriate. If a three dimensional preview is offered, it should reuse the same object assets and scientific conventions as the comparison. Do not maintain a separate inaccurate model just for encyclopedia decoration. The preview needs rotation and lifecycle cleanup. Available text languages can be fewer than interface languages during early content work, but fallback must be explicit. The initial catalog supplies Spanish and English summaries. Other interface languages can show a clearly identified English original where a local summary is missing. Do not claim full catalog translation merely because all navigation labels are translated. Expanding high-quality multilingual content is a separate curation task.

## 34. Details and compatible property comparisons

Details should show dimensions and definitions for all selected objects. Additional properties should appear when they are meaningful across the selected family. Density is useful for planets; area is useful for territories; population can be useful for compatible city scopes and dates. A property field contains its value and unit. The interface should not compare unrelated quantities simply because both are numbers. A building's number of floors is not a planetary density, and a galaxy's distance is not its diameter. Missing values should remain missing rather than being shown as zero.

The current details implementation displays area or density only when every selected object has the corresponding field and shares a broad category. Future refinements can use stricter family, basis, unit, and temporal compatibility. When adding rankings, explain the criterion. A larger city by land area can have fewer inhabitants; a larger planet can have lower density. Those relationships should be explained through sourced data, not conjecture about typical skylines. Do not estimate average building height from population density. Do not derive physical mass from illustrated volume unless the model, density, and geometry support that calculation. Keep the basic comparison clean, with these richer facts available on demand.

## 35. Interface languages and automatic resolution

The initial interface supports Spanish, Catalan, English, French, German, Portuguese, Italian, Chinese, Japanese, and Hindi. The owner's spoken reference to the language of India is implemented as Hindi; do not call that language Hindu in UI labels. Language choice defaults to automatic browser preferences. Iterate navigator.languages in preference order, match a supported base language, and fall back to English when there is no match. A manual choice overrides automatic resolution and is persisted locally. Set the document language so assistive technology, text shaping, and browser behavior agree with the visible interface.

src/i18n.js contains translated interface strings and selected astronomical names. Object metadata can include additional names and summaries. A language key must not silently point to an unrelated language merely because a string is short. Translation validation checks the main interface dictionaries for missing entries. Family names, measurement descriptions, summaries, and scientific terminology also need proper translation as content work advances; dictionary completeness does not prove that every content field is localized. Chinese and Japanese need adequate layout for compact labels, while Hindi needs font support and line-height that preserves its script. Avoid ASCII-only processing that strips meaningful characters from names or exported files. Search normalization should not corrupt original displayed names.

## 36. Automatic theme and time assumptions

Theme options are automatic, morning, afternoon, and night. Automatic selection uses the visitor's local system clock and date, not a hardcoded deployment timezone or a server clock. The initial implementation approximates seasonal daylight without requesting a location. It is a visual heuristic, not a calculation of actual solar elevation everywhere on Earth. Do not claim geographically accurate sunrise from month and local hour alone. If exact daylight is later requested, add an explicit location method or a user-selected place and a documented astronomy calculation. Location access is unnecessary for the present basic theme feature.

Refresh automatic theme periodically so a tab left open can change from daytime to evening. A manual selection should remain fixed until the user changes it. Theme colors must preserve contrast for text, buttons, borders, and input states. The comparison stage can remain dark enough to display planetary textures clearly even when the surrounding interface is light. Do not invert photographs or scientific color maps merely to create a night theme. Reduced motion preferences should be respected independently of the theme. Theme transitions can be brief and subtle, but they must not create bright full-screen flashes or make the controls disappear during a change. Verify each theme visually on representative desktop and mobile layouts.

## 37. Inventory purpose and truthful coverage

The hidden inventory is the owner's technical view of what the project actually contains. It reads the effective catalog, including comparable and pending entries. Search and status filters help locate records. It shows identity, folder, category, family, parent, dimensions, measurement definition, measurement status, visual fidelity, assets, tags, source, and source retrieval date as appropriate. These are real project fields, not invented completion badges. The owner should be able to identify missing measures, absent textures, illustrative models, imported observations, and candidates for future research.

An inventory row is not proof that an entry is scientifically complete. Conversely, a pending record is useful even if it cannot appear in the central comparison. Preserve those distinctions in counts and exports. Do not inflate the number of measured objects by including unknown entries, generic duplicate variants, or model descriptors without dimensions. If a later review system is added, record what was reviewed, which sources were checked, what changed, and the actual review date. A build passing its validator is a technical integrity check, not a full scientific review. Technical and scientific states should be separate fields. The initial inventory does not pretend that every representative example has undergone a specialist audit.

## 38. Inventory exports and spreadsheet integrity

The initial inventory can export XLSX, CSV, JSON, and plain text, and offers the SQLite release file for download. Exports follow the current inventory filter so the owner can inspect a subset or clear filters to obtain all entries. JSON retains full metadata. Tabular formats provide stable named columns and SI values. Empty exports should still produce a coherent header or workbook. Preserve Unicode names and folder spellings. Do not export formatted kilometer strings as if they were raw meter values. Numeric columns in XLSX should remain numeric, including small exponential values.

The XLSX writer creates a legitimate ZIP container with workbook and worksheet XML. Text uses inline strings and is escaped as XML. Numeric values use numeric cells. Formula-like strings are stored as text, so an object name cannot inject an Excel formula. CSV strings beginning with formula markers are neutralized before export. Test special characters, line breaks, empty fields, scientific notation, and Unicode. Do not substitute an HTML table renamed .xls for a genuine workbook. The export module is lazily loaded and has no external runtime dependency. If a richer spreadsheet library is introduced, inspect its maintenance and vulnerabilities, and retain the no-service design. The app currently exports data; it does not import untrusted workbook archives.

## 41. Mathematical tests that protect the product

The meaningful mathematical tests protect proportions and definitions. Earth and Moon should preserve their known diameter ratio on the same scale. Elongated objects should preserve their width-to-height ratio. A lineup with more than ten objects should remain valid and horizontally accessible. Planck length compared with observable-universe extent should yield finite positive transforms and an honestly unresolvable small object. Null dimensions should stay null, and the empty lineup should not throw an error. A sphere's width and height should remain equal in the unrotated comparison.

Do not write tests that merely restate an implementation constant without protecting a user-relevant contract. Test a genuine edge case when changing scaling arithmetic, data conversion, or camera layout. If a new area comparison is added, test area preservation independently of lengths. If rings are added to the headline measure, test the new definition and update its labels. Formatting tests should distinguish raw SI values from rounded display strings. Very small values may use scientific notation; very large astronomical values may use light-years. Keep formatting separate from calculations so a rounded label cannot affect ordering or ratios. Tests are valuable when they catch a plausible conceptual error, not just when they raise a coverage percentage.

## 45. Licenses, attribution, and asset provenance

## 48. Improving scientific curation without hiding the initial limits

The initial release deliberately establishes the catalog infrastructure and a broad first set of examples. Its primary next task is scientific curation. Review entries in bounded groups. For each, confirm object identity, measurement definition, units, numerical value, uncertainty or representative range, source specificity, retrieval date, summary accuracy, and asset provenance. Where secondary dimensions are schematic, say so explicitly or move them into separate illustration metadata. A curated primary dimension should not lend unjustified authority to every surrounding field. Preserve a record of meaningful corrections when a value changes substantially.

Do not equate successful schema validation with scientific accuracy. The validator confirms structure, finite dimensions, local files, dictionary coverage, and generated output consistency. It cannot determine that a whale's chosen representative length is biologically appropriate or that a city's administrative area matches the latest official boundary. Add review metadata if useful, with honest states such as initial, source-checked, or specialist-reviewed and a real date. Avoid blanket claims that all entries were verified on one day just because the initial import ran then. Retrieval date records access or import context, while observation date and data reference epoch can differ. Those dates deserve separate fields when the science requires them.

## 49. Adding a curated batch of new objects

For a requested batch, first define its inclusion criteria. Eighty famous buildings, all moons with known physical parameters, a set of common bacteria, or two additional dog breeds are different projects. Determine likely authoritative sources, measurement conventions, and lawful visual assets before creating folders. Use stable IDs and alphabetically named canonical folders. Supply useful translated names and concise Spanish and English summaries at minimum until broader content translations are curated. A batch with a new family, renderer type, measurement convention, or geographic projection needs additional targeted checks. Update documentation where a new rule is introduced. Report the number of new comparable and pending records separately. Do not inflate scope with thousands of poorly sourced records merely because an API can return them. The owner's ambition is comprehensive, but it is intended to grow through thoughtful, useful additions that preserve the quality of the central comparison.

## 50. Future formats and richer three dimensional assets

Future realistic animals, ships, buildings, microscopic structures, and molecule models can improve the experience significantly. Prefer formats the browser can load reliably, such as self-contained GLB for textured meshes. Normalize measured bounds carefully and preserve the source object's intended axes. A model created for visual entertainment can have deliberately exaggerated proportions and should not automatically become scientific evidence. If a model lacks measured dimensions, use independently sourced catalog dimensions to scale it, and state that the mesh is illustrative. Embedded materials and textures should remain local so the published model does not unexpectedly call a remote host.

Level of detail, compression, and geometry simplification can keep the scene practical on phones. Introduce those capabilities with measured performance checks and transparent asset provenance. Do not provide a huge uncompressed mesh for a subpixel object. If complete mapping of a body is unavailable, do not synthesize an unmarked realistic far side and imply that it was observed. Neutral regions or clearly labeled reconstructed content are acceptable. Texture and model fidelity should be visible in the encyclopedia and inventory. A future realistic Sun can include physically motivated animation, but decorative motion must not be described as live observed solar activity unless a real data feed and its limitations are deliberately implemented.

## 51. Area, volume, mass, and future comparison modes

The original emphasis is size, and the initial implementation compares lengths and displayed extents. Future area or volume modes can be useful, but they require their own definitions. If two territories have areas A and B, their equal-area shapes should occupy pixels in proportion to A and B; their characteristic lengths then scale with square roots. If two spheres have diameters d and e, their volume ratio is the cube of d divided by e only under the sphere assumption. A generic animal mesh is not a reliable measured body volume. A reference to mass requires actual mass data rather than a visual inference from shape.

Each new mode should have a clear selector, explanatory labels, and meaningful tests. Avoid a view where some items follow length scaling and others area scaling without an explicit comparison contract. A city represented as an equivalent-area square can be compared by its characteristic side length while the encyclopedia explains the construction. A separate area table can compare its area directly. These concepts are related but not identical. Adding technical sophistication should help users understand rather than make the visual language inconsistent. Preserve the simple default experience while allowing interested visitors to inspect the richer definition. Store enough metadata to reproduce the calculation and distinguish source values from derived ones.

## 52. Handling orientation, silhouettes, and bounding boxes

An object's visible shape and its declared physical dimensions need a coherent relationship. An SVG's viewBox can contain generous empty margins that make the object occupy only part of its nominal width. If the application scales that entire box as the declared dimension, the actual drawn outline will be too small. Trim or deliberately define the silhouette bounds so its primary extent matches the metadata. Preserve that decision in the asset-generation or curation process. A shape may be illustrative, but the declared reference length still needs a consistent visual extent. Do not use the whitespace of an icon as a measurement boundary.

Similarly, GLB normalization needs correct bounds after transforms are applied. A model with a misplaced root, hidden far-away helper, or an animation rig can have a bounding box unlike the actual object. Inspect it before treating the box as a physical envelope. Measured axes can be associated with a specified orientation; rotating the object changes its projected extent while preserving its world size. A flat two dimensional view should start in the documented comparison orientation. If users can rotate a long ship end-on, its apparent projected length will shrink, and details should still show the actual declared length. Camera perspective must not introduce another unrelated scaling change. These are geometric issues, not reasons to modify the catalog values to make one screenshot look attractive.

## 53. Dates, changing facts, and temporal data

Source retrieval date, observation epoch, publication date, construction completion date, and review date are different. A generated date should not stand in for all of them. Moon discoveries and designations change; ships enter service; buildings reach planned heights; population estimates are revised; scientific parameters improve. When updating such content, use current primary sources and identify the applicable date. Stable reference conventions such as a deliberately selected 1.75 meter person do not need a false observation epoch. Natural constants may be based on a particular CODATA adjustment and should be documented when relevant.

The browser's local clock drives theme selection, but it should not automatically update scientific measurements. A visitor opening the site next year does not make a frozen census value current. If live updates are later desired, design a controlled repository data refresh rather than a browser scraping layer. Each refresh should produce reviewable changes with sources and validation. Cache versioning and stale assets must be considered when deployments change the catalog or document. Do not infer the owner wants a recurring automation merely because the data can age. Schedule or monitoring work requires an actual request. The static design remains useful when its dates and definitions are honest and visible.

## 54. Error handling and recovery paths

Errors should preserve as much useful functionality as possible. A missing optional texture can fall back to a silhouette or colored shape while the measurement remains available. A missing mandatory catalog file should produce a retry action. A malformed metadata entry should fail the build with the specific object identity so it can be corrected before publication. A failed XLSX export should be surfaced rather than falsely announcing a successful download. A failed clipboard operation should reveal a selectable link. Do not swallow every exception and leave the user guessing whether the operation happened.

At the same time, avoid exposing raw internal stack traces inside ordinary public controls. Technical details can be logged for development and described in the internal documentation. The visitor needs a concise explanation and a practical next action. When graphics fail, choose the vector fallback; when an object lacks a measurement, explain pending status; when search has no matches, allow changing the query or browsing another category. A long lineup should remain navigable even if one model fails. Verify that asynchronous failures do not erase unrelated selections. Fault tolerance should be designed around the product's core information, preserving dimensions and meaningful context while optional visual richness degrades gracefully.

## 57. Practical review questions for the next contributor

Before accepting a substantial change, consider what the user will understand from it. Does the visible object occupy the correct shared scale? Does its measurement definition match the number and model? Can the user find it quickly in the picker? Is the image an observed resource, a reconstruction, or an illustration, and is that distinction discoverable? Does a missing value remain missing? Are newly added geographic facts based on compatible boundaries? Are theoretical physics references distinguished from observed object diameters? Does the interface remain useful when graphics or clipboard access fail?

Then consider whether the project remains maintainable. Can the changed entry be rebuilt from its folder? Are local assets distributed lawfully? Does SQLite agree with metadata? Are links stable? Is the deployed application independent of sibling repositories? Are browser preferences and public catalog data separated? Are the inventory and superprompt current? Did the change add an unnecessary external service, hidden network request, or duplicate source of truth? These questions are a review aid, not a requirement to produce a long checklist in every user-facing response. Apply judgment proportional to the change. A corrected source URL and a new graphics engine feature need different verification depth, but both should preserve the product's central promise of clear, trustworthy relative scale.

## 58. Working with the owner's references

The original brief mentioned a longstanding simple space-object comparison, the owner's Universal project, the toolbar pattern in Bum, and internal tooling in Formulas, Arteteca, and Games. Translate the underlying product intent into this project's architecture rather than mixing unrelated implementations into a fragile collection of borrowed panels.

## 59. Keeping the public experience simple as the catalog expands

The amount of information behind Sizes can grow dramatically without making its first screen complicated. Preserve two familiar default objects, a central scene, a clear add action, and restrained suggested comparisons. More categories can enter the picker without becoming additional permanent toolbar buttons. More properties can enter details without turning every selected card into a spreadsheet. More content can enter the encyclopedia without making it mandatory reading before comparison. A visitor should understand the basic operation within seconds. The owner explicitly wanted depth behind a visually simple interface.

Large catalogs also need sensible defaults. Featured examples are a discovery layer, not a restriction. Category representatives can make an unfamiliar family approachable. A search result can expose the right family and parent. Saved URL comparisons can provide ready-made educational sequences such as the Solar System or microscopic structures. Consider performance and mobile interaction before expanding visible grids. Load only models that are currently relevant, and avoid opening several expensive previews simultaneously. When adding a new capability, ask which existing action it naturally belongs to rather than immediately adding another prominent button. The objective is a coherent comparator that grows in depth while preserving visual calm and the truth of its proportions.

## 60. Durable north star for Sizes

Sizes should let someone place a familiar thing beside an unfamiliar thing and understand their relationship. A person next to an elephant, a whale next to a ship, Earth next to the Moon, or a virus beside a cell can communicate an enormous amount through a good shared scale. The broad catalog links the owner's specialist projects into a common view of how things fit within the world and universe. That ambition is best served by a reliable foundation: explicit definitions, internal SQLite, canonical folders, local assets, accessible interaction, graceful fallback, careful translations, and maintainable documentation.

Future contributors should expand the project with confidence while keeping those principles intact. Improve realism where the evidence and assets support it. Add new families where they make discovery easier. Curate source quality and uncertainty as deliberately as visual quality. Keep the internal inventory truthful so the owner can see what remains unfinished. Preserve this superprompt as a practical explanation of the actual system rather than an aspirational claim that every feature already exists. A beautiful illustration and a trustworthy measurement can coexist when their roles are clear. The central promise remains straightforward: choose objects, see their sizes together, and understand the proportions without hidden distortions or unnecessary infrastructure.
